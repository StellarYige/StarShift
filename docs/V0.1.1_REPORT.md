本文件随实测回填。所有输入均为仓库自制样例，诊断不记录用户文档内容或文件名。当前尚未创建 v0.1.1 标签或 Release；线上修订版结果待部署后补齐。

## 修复与行为

- DOCX 仍采用同批串行复用、每批结束释放引擎的策略，不增加空闲引擎或持久缓存，不更换引擎和中文字体。适配页面、脚本及 UNO 线程有 `v=0.1.1` 标识；引擎和字体 URL 保持稳定。
- 进度增加可选阶段和读取字节信息，原有文件／页数语义保留。下载总量不可靠时不展示百分比；WASM 保留流式加载。
- 下载、初始化、不兼容、文档错误和超时分别提示。引擎级错误停止本批重新初始化，保留文件和设置供显式重试；单份坏文档不妨碍后续有效文档。
- 损坏 PDF 失败时销毁 loadingTask / Worker；取消信号覆盖打开、取页和渲染，异步任务只更新所属工作区。
- 预览翻页清除旧图和旧错误，关闭预览取消加载；重复 ZIP 下载复用一个已准备的结果，结果变更或清空时撤销 URL，并提供直接下载链接。
- 引擎销毁时关闭消息端口、终止 Worker、清理定时器和 Blob URL；不以 iframe 消失代替内存回收证据。
- Windows WebKit 实测暴露图片转换依赖 Worker Canvas 的问题，增加本地 DOM Canvas 回退；PDF 拼装仍在可取消的 Worker 中完成。JPG、PNG、WebP 的 MIME、透明度、方向及下载内容断言通过，没有新增编码依赖。
- 修复首屏 hash 变化早于监听注册时无法切换工具的竞争；修复横屏预览底部按钮被裁切，补齐窄屏图标按钮的可访问名称。
- 计时器跟踪保留浏览器原有回调接收者。此前 Chromium 曾在引擎运行时已初始化、UNO 线程尚未就绪时超时；保留[当时状态](evidence/v0.1.1/chromium-timeout-diagnostic.json)。修正回调上下文后多次十轮验证通过，但没有据此宣称已证明所有初始化停顿的根因。
- 内存实测进一步发现：清空数组后，React 上次渲染仍保留最后一个 File 和 Blob；改为卸载持有文件状态的工作区，转换设置由外层保留。修复后十轮页面 GC 检查两类弱引用存活数均为 0，并新增四项工具的回归断言。
- Firefox / WebKit 的实际失败发生在大 WASM 分配之后，连续重试的进程内存显著增加。依据已实测的能力限制，在分配前检查 OffscreenCanvas 和当前引擎的 `clipboard-read` 权限名称支持；只将不支持名称的 TypeError 判为不兼容，不把用户拒绝权限当作不兼容。不记录浏览器永久黑名单，也不建立空闲引擎或持久缓存。

两项回归先在 v0.1.0 复现：[基线失败记录](evidence/v0.1.1/baseline-regressions.json)。损坏 PDF 后活动 Worker 为 1；连续三次 ZIP 下载的活动 URL 为 3、4、5。修订版对应测试通过。

同一中文样例的两页 PDF 经同一独立渲染器生成 PNG，修订版与 v0.1.0 两页 SHA256 分别相同，亦已检查页面截图；结论仅限自制样例，不外推任意 Word 文档。证据：[逐页比较](evidence/v0.1.1/layout-comparison.json)、[第一页](evidence/v0.1.1/docx-page-1.png)、[第二页](evidence/v0.1.1/docx-page-2.png)。

## 测量方法

基线由 `v0.1.0`（`628daa9ebc1a733954f7824a046cf13ab0e5af4f`）独立工作树构建。前后使用同一台 Windows 设备、Chromium 153.0.8010.12、两份相同中文表格分页样例及相同测量脚本。每轮新建浏览器配置测冷启动，再重启浏览器并复用磁盘配置测再次访问，然后同一页连续五批。每批两份文件；本地各五轮，线上各三轮；缓存过期另测。

计时范围是点击转换至两份结果完成，首页和文件选择在此前完成。冷启动配置在打开站点前没有 HTTP 缓存或既有 Service Worker；站点正常注册隔离所需的 Service Worker，首页注册和刷新不计入转换耗时。性能样本每批检查两份结果完成，并独立校验首份 PDF 的中文、表格几何、图片和分页；原有 DOCX 回归另对同批两份输出（含字体替代样例）逐一执行内容断言。网络使用 [CDP Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/) 及[递归目标观察](https://chromedevtools.github.io/devtools-protocol/tot/Target/#method-setAutoAttach)，覆盖页面、同进程 iframe、Worker 和 Service Worker；不做请求拦截、不禁用缓存、不暂停调试目标。重复 CDP 会话按请求标识、URL 和时间去重；排除外层 Service Worker 响应，只计底层网络／缓存请求。

接收量来自 `loadingFinished.encodedDataLength`，包含协议报告的传输开销；解码体积来自 `dataReceived.dataLength`，缓存响应另列，不能拿资源清单尺寸替代传输量。缺少完成事件时接收总量记为 `null`（未测得），另存已知下界；缺少 body 事件时解码体积同样记为未测得。304 的响应开销计入网络，复用正文归入缓存。首次文档检查无法从旧版观察点中与 iframe 适配准备完全分离，因此独立值记为“未测得”；同批后续检查可测。资源请求覆盖时间与编译、初始化重叠，不应相加。原始事件中保留导入、导出及 UNO 就绪时间。

性能样本与故障注入、资源计数、OS 内存采样分开运行。初始校准中暂停 CDP 新目标会阻止 Service Worker 启动；该校准失败不计为产品性能样本，记录保留。额外消息端口监听和大型 WASM trace 正文记录也曾扰动生命周期测试，改用 DOM 阶段观察与资源计数；保留[旧观察器超时记录](evidence/v0.1.1/harness/port-observer-timeout.md)，不把它冒充已定位的产品取消缺陷。

线上基线首轮记录到 `soffice.js` 请求的 `ERR_FAILED` / `ERR_CONNECTION_ABORTED`，原版等待后对下一份重新初始化，270.181 秒验收时只有一份结果；该轮为失败。其他二十批成功。

最终修订版本地 35 批中 34 批成功，第五轮再次访问停在初始化、未收到 UNO 就绪，240 秒后产品提示超时并停止本批，270.103 秒验收时没有输出。原文件保留，同页之后五批显式重新转换均成功。该样本一个 Worker 脚本请求缺少完成记录，接收总量为“未测得”，只报告已知下界；不能据此断言网络失败或根因。这个偶发初始化问题尚未定位，不能宣称所有引擎停顿已经修复。见[原始失败](evidence/v0.1.1/harness/final-performance-failure.json)。

随后在同一设备、同一方法下对未改动 v0.1.0 再测完整五轮，33/35 批成功：冷启动 16.613［12.328–17.188］秒，再次访问 12.209［10.907–18.947］秒，连续批次 10.809［9.882–20.979］秒。第一轮第五批在 19.387 秒收到初始化错误，旧版随后处理下一份，最终只有一份结果；第二轮第五批无输出且页面只读查询也无响应，270.049 秒验收失败后结束该测试浏览器才继续。该次事件明细未测得，没有补造阶段数据。对照说明早期约 8 秒基线不足以代表后续设备状态，也证明旧版存在初始化失败；样本量不足以证明两个版本失败率相同，更没有确定两种停顿的同一根因。见[同期基线](evidence/v0.1.1/performance/baseline-local-contemporary.json)、[失败明细](evidence/v0.1.1/harness/baseline-local-contemporary-failures.json)、[页面无响应处置](evidence/v0.1.1/harness/baseline-local-contemporary-unresponsive.json)。结束父进程后另发现该配置的 renderer 和 crashpad 未退出，按精确配置目录核对并结束；它们可能影响后续对照轮次，未测其 CPU / 内存占用，不能用该补充对照单独归因代码性能。见[残留进程记录](evidence/v0.1.1/harness/baseline-orphan-cleanup.json)。测量脚本随后为失败后的只读诊断和退出增加时限，并在计时外检查及结束所属测试配置的残留进程；正常计时、网络和缓存方法不变。

中间修订版也完成过五轮及五组相邻配对，但它们早于最后的清空和能力预检修复，保留为诊断历史，不冒充最终验收。在相邻配对中冷启动只有 3/5 组改善（旧版中位数 12.576 秒、中间版 14.953 秒）；再次访问 5/5 改善（16.654 → 12.078 秒）。旧版成功样本也曾达到 40.023 秒。整体不满足预定的稳定提速判据，未引入字体并行或其他性能优化。见[配对原始运行](evidence/v0.1.1/performance/paired-runs.json)、[比较](evidence/v0.1.1/performance/paired-comparison.json)。

另隔离尝试了基于 [ZetaJS 官方启动接口](https://github.com/allotropia/zetajs/blob/main/docs/start.md)的有序 Worker 脚本候选，用于检验动态模块加载是否相关。候选先通过 14 项原有回归和十轮内存检查，但性能试验第三轮连续第一批仍未收到 UNO 就绪，270.083 秒验收失败。记录 22 批（21 成功、1 失败）后停止剩余实验，**未采用候选代码**，也不把它计入最终版五轮样本。它没有证明初始化停顿的根因或修复，发布版本保留已验收的适配实现。见[候选否决与代码指纹](evidence/v0.1.1/harness/bootstrap-candidate-rejected.json)、[部分样本](evidence/v0.1.1/performance/revised-local-classic-candidate.json)、[只读状态](evidence/v0.1.1/harness/revised-local-classic-candidate-state.json)。

本地服务器 `Cache-Control: no-cache` 且不提供验证器，冷启动和再次访问均实收约 267.5 MiB。Pages 返回 `max-age=600` 和 gzip；成功冷启动实收约 92.6 MiB，再次访问及连续批次实收为 0，仍需初始化引擎。这里的 0 是 CDP 网络接收结果，并不表示无需解码、编译、初始化或占用内存。

本地冷启动字体等待中位数 286.445 ms（268.395–340.515 ms），到 UNO 就绪中位数 7,112.530 ms。字体串行等待确实存在，但占比不足 5%；没有据此引入并行准备，也不声称已取得稳定提速。性能改动仍须满足五对样本至少四对改善、目标阶段中位数至少改善 5% 且排版与资源验收通过。

初次完整矩阵有 15 项失败，涉及初始化超时、WebKit Canvas 和窄屏按钮；修订后完整矩阵剩两个 WebKit 工具切换失败，修复 hash 竞争后九项定向复测通过。截图复核发现横屏页脚裁切并修复；额外复测曾有一次 Firefox 首页加载未出现 header，未进入预览流程，相同产品代码随后通过，未确定该次启动失败根因。iPhone 的初始 100% 页脚容器可见性断言还包含圆角裁切，改为对翻页和下载控件逐一要求 100% 可见，横竖屏均通过。原始失败均保留：[首轮](evidence/v0.1.1/matrix-first-attempt.json)、[修订轮](evidence/v0.1.1/matrix-revised-attempt.json)、[路由复测](evidence/v0.1.1/matrix-route-recheck.json)、[预览首轮](evidence/v0.1.1/matrix-preview-first.json)、[预览复测](evidence/v0.1.1/matrix-preview-recheck.json)。

实际加载并启动固定引擎的诊断确认两项限制：Firefox 155 在引擎查询 `clipboard-read` 权限时拒绝不支持的 `PermissionName`；Windows Playwright WebKit 26.6 报告不能将 `#qtcanvas` 交给 pthread，缺少该引擎需要的 OffscreenCanvas 支持，UNO 无法就绪。最终版在同样能力检查失败时提前提示“不兼容”，不再等待大 WASM 分配；同时保留适配层的运行时错误识别，不把普通初始化错误或超时一律归为不兼容。最终矩阵记录是否在引擎资源请求前拒绝。最初真实引擎启动证据：[Firefox](evidence/v0.1.1/firefox-engine-diagnostic.json)、[WebKit](evidence/v0.1.1/webkit-engine-diagnostic.json)。剪贴板权限差异也见 [Mozilla Clipboard API 文档](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)。这些结果不代表真实 macOS Safari 已经测试，也不计为 DOCX 转换通过。

Chromium 十轮、Firefox / WebKit 各三轮转换、取消、重试、预览、清空和切换工具已通过。每轮结束活动 Worker、Blob URL、长定时器和 iframe 为 0，MessagePort 保持 2（页面框架基线），没有逐轮增长。最新逐轮计数见[最终矩阵](evidence/v0.1.1/matrix-local.json)；[早期十轮计数](evidence/v0.1.1/chromium-lifecycle.json)也保留。故障测试覆盖下载、脚本 404、初始化、超时、隔离不可用及实际重试，之后实际转换其他四项工具；损坏文档位于两份好文档之间时不重启引擎。资源加载、初始化、导入、导出、缩略图、预览和 DOM 编码取消后，旧任务不能回写新工作区。新增清空测试在四项非 DOCX 工具逐一验证输入和输出清空、设置保留；Chromium 经页面 GC 后被观察的 File / Blob 弱引用均为 0。Firefox / WebKit 无法同样强制 GC，弱引用存活数不作泄漏断言。

Chromium 首次最终内存运行在第二轮初始化超时后停止，[失败记录](evidence/v0.1.1/harness/memory-final-first-attempt.json)保留。随后相同产品代码完成十轮清空，其中第八轮有一次超时，保留输入后显式重试成功，即 11 次转换尝试中 10 次成功、1 次超时；不把资源检查通过写成没有转换失败。每轮清空和页面 GC 后，累计观察的十个 File 和十个输出 Blob 弱引用存活数均为 0。页面 JS 堆从 2.5 到 3.8 MiB，进程树工作集基线／峰值／最终分别为 352.6／1234.0／542.6 MiB，没有逐轮累积整个引擎，但也没有回到全部初始值。

清空修复前的中间版每轮页面 GC 后仍留一个 File 和一个 Blob；能力预检前，Firefox 和 WebKit 第三轮清空后私有内存分别达到 6382.7 和 6737.0 MiB。预检避免了已知不兼容路径的大 WASM 分配；这不是 Firefox / WebKit 的 DOCX 转换成功。OS 私有内存包括浏览器及子进程，工作集相加可能重复计算共享页，页面 GC 不覆盖全部 native / WASM 分配。这些结果只支持所测次数中的回收趋势，不能证明内存完整返还操作系统。证据：[修复前](evidence/v0.1.1/memory-before-final-clear/memory-summary.json)、[最终汇总](evidence/v0.1.1/memory-summary.json)、[Chromium](evidence/v0.1.1/memory-chromium.json)、[Firefox](evidence/v0.1.1/memory-firefox.json)、[WebKit](evidence/v0.1.1/memory-webkit.json)。

## Actions、路径和发布

已按 GitHub 官方标签读取 `action.yml` 并固定 SHA，源码证据见 [Action 版本核对](evidence/v0.1.1/action-versions.json)。五个 JavaScript Action 使用 Node 24；Pages 上传是组合 Action，其内层上传器也是 Node 24。遵循 [GitHub Node 20 迁移说明](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/)，不通过关闭警告处理迁移。项目 Node 24 与 npm 依赖固定版本保留。
