# DOCX 初始化等待修订（未发布）

基于已发布的 `v0.1.1` / `89ffa63`。本轮只处理启动阶段的观察、无进展提示和恢复说明，版本保持 `0.1.1`，未创建新标签、Release 或项目发布包。

先复核原始记录：[旧版线上下载失败](evidence/v0.1.1/performance/baseline-online.json)、[v0.1.1 最终本地失败](evidence/v0.1.1/performance/revised-local-final.json)、[运行时快照](evidence/v0.1.1/chromium-timeout-diagnostic.json)。它们不能合并成同一种故障：线上样本存在明确的脚本请求错误；最终本地失败在约 6.149 秒之后没有新的初始化通知，直到 240 秒产品超时，未收到 `ready` 或进入导入。某个 Worker 的 `zetaHelper.js` 请求缺少完成事件，但这不足以断言下载失败。

较早快照还记录到运行时已初始化、依赖计数为 0、已创建两个 Worker，但长时间没有文档服务就绪。已创建不等于已加载，依赖为 0 也不能证明 UNO 可用。现有证据不足以确定模块加载、线程握手或其他引擎内部步骤中的哪一处是根因；先前已否决的启动候选没有重新采用。原始文件指纹与本轮复核摘录见 [证据索引](evidence/docx-startup-stall/prior-evidence.json)。

新增观察使用固定引擎已有的回调、消息和资源完成通知：

| 阶段 | 可观察的边界与限制 |
| --- | --- |
| 资源加载 | 固定五项资源的完成通知；字体读取或 XHR `loaded` 增长才记录下载前进。WASM 的流式响应不克隆、不提前读取，过程中可能没有可测的字节进展。 |
| WASM 运行时初始化 | 资源完成后尚未收到 `onRuntimeInitialized`；实际回调记录运行时就绪，保留原回调接收者和调用。资源加载与初始化可重叠，完成通知也可能晚到。 |
| Worker 启动 | 记录创建数及固定 `loaded` 消息确认数，等待 ZetaHelper 的启动握手；不读取其他消息内容。 |
| 文档服务就绪 | ZetaHelper 启动回调之后等待现有 UNO 适配线程的 `ready`，随后才允许导入文档。 |

诊断只含枚举、布尔值、计数和时间。下载前进序号是事件计数，不是传输字节数或百分比。没有持久化用户文件名、内容、引擎异常全文或诊断历史，也没有增加外发接口。现有测量脚本仅补充这些启动字段；原 CDP 网络观察和输出断言继续复用。

页面每秒检查一次观察状态，约 30 秒没有新的阶段、计数或下载进展时显示等待说明，不中断任务。重复相同状态不会重置等待时间。提示中的秒数以十秒为单位更新，并跳过相同 UI 状态，避免每秒重复播报。最近五秒仍收到下载数据时明确显示这一点；资源阶段缺少连续数据观察时说明“部分下载无法持续报告进度”，不宣称引擎已停顿。若阶段或下载重新前进，等待提示清除。

保留 240 秒启动上限及 180 秒文档处理上限。启动超时显示最后可见阶段，仍有下载进展时单独说明，不再统一要求减小文档。取消说明输入和设置仍在，再次开始转换会创建新引擎；等待提示和超时都不会发起自动重试。沿用原有同批串行复用和每批结束释放；新增观察器与父页面定时器在就绪、取消、失败或销毁时结束。

字体注入、WASM 流式加载、ZetaHelper 启动调用和 UNO 线程脚本的加载顺序没有改变。仅给已修改的页面／适配脚本使用 `0.1.1-startup.1` 缓存标识，原引擎、字体和 UNO 线程 URL 保持稳定；这不是新的产品版本。

验证在 Windows 11（build 26200）、Chromium 153.0.8010.12、Node 24.18.0 上执行：

- 类型检查与生产构建通过，原有 7 项单元测试通过。构建出现 Vite `PLUGIN_TIMINGS` 提示；Playwright 的 `NO_COLOR` / `FORCE_COLOR` 提示仍保留，未关闭警告。
- 原有 [14 项回归](evidence/docx-startup-stall/e2e.json)通过，包含中文、表格几何、图片、分页、字体替代、预览、下载及无文件数据外发断言；原单元与回归文件未改。
- 复用的 [9 项 DOCX 回归](evidence/docx-startup-stall/existing-docx-regression.json)通过：下载／脚本／初始化／超时故障恢复、坏文档不重启同批引擎，以及加载、初始化、导入、导出期间取消后使用其他工具。
- [6 项针对性测试](evidence/docx-startup-stall/targeted.json)通过：四个启动阶段的等待及取消，两种启动超时说明；每项均实际重新转换两份 DOCX、独立验收首份输出，随后切换其他工具并清空。Worker、iframe、Blob URL 和定时器归零，MessagePort 回到页面基线。这里只证明所测资源计数回收，不声称全部 native / WASM 内存返还操作系统。

另对两个用例补充[进展恢复复查](evidence/docx-startup-stall/progress-recheck.json)，均通过：恢复下载后，同一引擎的等待提示消失；重复相同依赖状态不会重置等待时间。保存并检查了 [390 px 窄屏提示截图](evidence/docx-startup-stall/startup-wait.png)，它是浏览器视口模拟，不是真机测试。

针对性测试使用人为阻断及父页面观察时钟偏移，未修改引擎时钟或原生总时限，不计为自然停顿或性能样本。首轮 4 通过、2 失败的[原始记录](evidence/docx-startup-stall/targeted-first.json)保留：原测试在 Worker 阻断点尚未确认时快进观察时钟，仍可能收到正常启动进展；下载超时断言也可能早于最后一次时钟跳变后的新下载观察。修订测试先确认实际阻断点或新读取通知，相同产品代码随后 6 项通过，没有通过修改超时或忽略断言处理这些失败。

不注入故障、不拦截请求的一轮真实观察为冷启动、重启浏览器后再次访问、同页五批，共 **7/7 批成功**；本轮没有自然复现偶发停顿。每批最终均记录五项资源完成、运行时已初始化、两个 Worker 已加载及最终 `ready`，输出验收、隔离和 iframe 释放通过。原始数据见 [启动观察](evidence/docx-startup-stall/startup-observation.json)，阶段摘录见 [汇总](evidence/docx-startup-stall/startup-summary.json)。

这七批中，最后一个资源完成通知晚于运行时就绪回调，因此没有观测到单独的 `wasm` 等待区间；不补造其耗时，也不把各阶段相加。资源结束后仍未完成运行时初始化的情况另由明确标记的故障注入覆盖。批次成功、显式重试成功及等待提示通过，均不能证明偶发停顿根因已经修复或失败率下降。

仍需保留的限制：启动停顿根因未定位；流式 WASM 下载不是始终有可观测进度；整个页面线程失去响应时，提示和取消也可能延迟。本轮没有真实手机或 macOS Safari 操作，没有新增真机通过结论，原[人工清单](MOBILE_MANUAL_CHECKLIST.md)保持待验证。
