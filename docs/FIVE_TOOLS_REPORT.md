# 星易五工具完善记录（未发布）

本轮从 `19a49db` 开始，验证日期为 2026-09-12 至 2026-09-13。保留 React、现有转换引擎和中文字体，产品版本仍为 `0.1.1`。改动按功能分别本地提交；未推送、部署、打标签、创建 Release 或项目发布包。本文区分功能通过、性能结论和仍未解决的限制，不把显式重试成功当作 DOCX 根因修复。

**已经完成的行为。** 文件选择后立即进入待检查队列；格式、空文件、单文件上限及批次上限的跳过原因集中显示，文件检查和缩略图状态分开。默认处理等待、失败及取消项，成功结果保留；“全部重新转换”明确替换当前结果。单项重试沿用原输入 ID，只替换关联结果，保留其他成功输出、排序、旋转和设置。合并任务整体重试，遇到无效来源会明确失败。

尺寸、质量、边距和页码语法在设置处提示并阻止无效转换；每份 PDF 解析后单独报告页码越界。清空保留设置，切换工具释放文件与结果。桌面设置和进度保持可见；手机增加底部开始／取消及结果入口，预留安全区。常用按钮至少 44×44 CSS 像素，辅助文字至少 12px，保留焦点样式和适度播报。

[独立绘制计时](evidence/five-tools/performance/preview-paint.json)在触发按钮进入视口、后台任务结束后记录捕获阶段点击至图片解码完成后的动画帧。它不含 Playwright 自动滚动与等待轮询，也不是物理屏幕扫描延迟。两版逐页渲染尺寸完全相同，打开加五次翻页创建的 Worker 为基线 6 个、修订版 1 个。首次绘制的五组结果没有稳定退化，未声称改善。按时间脚本整段统计的“打开预览”仍为 1262→1393ms（慢 10.4%）；这个包含自动滚动和轮询的差异原样保留，不能拿不同计时边界互相相减或直接归因于解析。

首轮曾发现弹窗遮住页面后缩略图仍在生成，已按[诊断记录](evidence/five-tools/performance/preview-diagnostic.json)暂停隐藏缩略图，同时维持原预览像素细节。第一次 PDF 复测有一项超过脚本的 5 秒翻页等待上限，[失败样本保留](evidence/five-tools/performance/paired-pdf-first.json)，当时没有保存足够现场来确定这一次延迟的原因。随后修订界面避免旧图片被新页码短暂标记，计时等待真实的新图片，使用与功能回归一致的 20 秒上限并补充失败现场字段；最终五组没有失败，没有删除慢样本。

即时反馈在所测桌面样例中的 P95：文件选择 40.6ms、PDF 排序 32.5ms、图片排序 32.0ms、设置修改 39.3ms、发起转换 82.2ms，均低于 200ms。选择从文件输入 change 开始，排序／开始从实际事件到更新后的动画帧，设置含相同自动化操作开销。首轮 PDF 拆分开始曾有 250ms 样本；预览暂停修订后的五组该操作 P95 为 82.2ms，原值保留。这些结果不代表全部设备和任意复杂文件。

另做[同页连续三批图片内存观察](evidence/five-tools/performance/image-memory-trend.json)，每批均实际生成 PDF。清空及页面 GC 后私有内存为 183.1、179.3、180.8 MiB，30 个累计观察的 File、33 个 Blob 的活引用最终全部为零，没有观察到持续的私有内存增长。JS 堆为 3.4、3.6、3.7 MiB，包含有意累计的弱引用测量记录，不把小幅增长单独判成泄漏。

**已保留的失败证据。** [首轮 120 项矩阵](evidence/five-tools/matrix-first.json)为 75 通过、30 明确跳过、15 失败；不删除或改写成最终通过。失败包括旧测试把后台缩略图当作阻塞任务、过早执行 File 引用断言、WebKit 流式图片组装错误，以及 Chromium 153 的 DOCX 启动停顿。

WebKit 的原因已通过实际观察定位：懒加载 PDF 模块经公共 helper 反向导入 Worker 入口，入口执行两次，清空了逐张确认状态。局部解除该循环后，[入口执行次数从两次变为一次且实际输出成功](evidence/five-tools/failures/webkit-entry-observation.json)，[WebKit 与手机模拟复验 21/21 通过](evidence/five-tools/webkit-fixed.json)。后续最终复验单独记录。

File 引用首轮检查发生在异步 PDF 打开／销毁尚未退栈时。清空入口同步取消并丢弃拥有文件的状态；测试同时保留即时计数和有界等待后的计数，再在 Chromium 页面 GC 后要求归零。[针对性复验](evidence/five-tools/fixed-lifecycle.json)中 PDF 整理约 476ms 后归零，其他三项工具即时检查已为零。这个断言只证明可测 JS 引用已释放，不证明全部 native／WASM 内存返还操作系统。

DOCX 停顿根因仍未解决。[已有启动记录](DOCX_STARTUP_STALL.md)及本轮失败都不足以确定资源下载、Worker 加载／握手或引擎内部步骤中的具体原因。本轮没有改启动顺序、自动重试、240 秒启动上限或 180 秒文档处理上限。保留 30 秒无进展提示、下载恢复时撤销提示、取消及显式重新初始化；“266 MiB”明确标为解压后资源体积，实际传输另行观察。诊断继续只记录阶段、计数、布尔值和时间，没有增加文件数据外发。

本轮已安装 Chrome 152 的资源循环第六轮也发生[工作线程启动超时](evidence/five-tools/failures/chrome-152-round-6-timeout.md)，不能把问题范围限定在 Chromium 153。未发现足以支持某个启动顺序修改的证据，因此没有试改引擎启动逻辑。

复用原测量脚本完成一轮[无故障注入的自然观察](evidence/five-tools/docx-natural/five-tools-natural.json)：冷启动 8240ms，再次访问 7746ms，同页五批分别为 7028、6021、6053、7067、5959ms；每批两份 DOCX，7/7 批通过实际输出、隔离与 iframe 释放断言。最后均观察到五项资源完成、运行时初始化、两个 Worker 加载和最终 ready。自然样本中的资源完成通知与运行时就绪重叠，没有单独的 WASM 等待区间，不补造该阶段耗时；四个阶段的独立等待另由已标记故障注入覆盖。这七批成功不作为根因修复或失败率下降证据。

该自然观察使用本地未压缩、`no-cache` 静态服务器，CDP 实测接收量约 280.5 MB／批，含协议报告的其他资源和响应开销，缓存命中为零；不是线上传输承诺，也不是把 266 MiB 清单体积冒充下载量。原始网络记录继续保留。
